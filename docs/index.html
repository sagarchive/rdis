It starts as nine words of machine code.

Nine little-endian arm64 instructions. Nothing here says it's a string hash yet.

Assembly

Decoded, split into blocks, cross-referenced.

Capstone decodes each word. rdis finds the basic blocks, labels the branch targets and records who jumps where.

C

Lifted back into C you can read.

The shift-and-add folds back into x8 + (x8 << 5), wrapped to 32 bits because it runs in a w register. The first argument becomes a char * because the loop reads bytes through it.

Checked by running it.

C that looks right can still compute something else. So rdis is tested by execution, on code a compiler has already optimized and vectorized.

  1. Compilea C function with clang at -O1, -O2 or -O3.
  2. Decompilethe binary with rdis.
  3. Compile the outputso it has to be valid C, vector code included.
  4. Run bothon the same inputs and compare every result.

Follow a function through the program.

The CFG answers “where can execution go next?” The Calls view answers “who calls this function, and what does it call?” Explore a bounded caller/callee neighborhood, including imports and unresolved targets, then jump into the function or export the graph for review.

Interprocedural, not just local flow.

Pick Callers, Callees, or Both and a depth from 1–4. The graph labels local functions, imports and unresolved targets separately. Resource limits are explicit; a truncated graph says so instead of pretending it contains every relationship.

One analysis surface across workflows.

Use the Calls toolbar mode, or request the same bounded graph from the CLI, in-app console, or MCP. The result includes DOT plus node/edge counts, depth and truncation metadata; it is not a claim that every indirect call has been resolved.

# Two call edges around parse_packet
rdis app.bin -f parse_packet \\
  --callgraph \\
  --callgraph-direction both \\
  --callgraph-depth 2 \\
  | dot -Tsvg -o calls.svg

# In-app console
callgraph parse_packet callers 2

# MCP tool
callgraph(path, func, direction="callees", depth=2)

Structs come back as structs.

Field accesses through a pointer argument become a declared struct with typed fields. A field loaded back into the same pointer is a pointer to the struct itself, so a linked list reads as one.

A linked list, from arm64.

int listsum(struct node *p) at -O2, decompiled. The next pointer is recovered as field_8.

struct s_100000350_x0 {   /* recovered from field accesses */
    int32_t field_0;   /* +0x0 */
    uint8_t _pad_4[4];
    struct s_100000350_x0 *field_8;   /* +0x8 */
};

int64_t _listsum(struct s_100000350_x0 * x0) {
    int64_t x8;
    int64_t t1;

    x8 = 0;
    if (x0 != 0) {
        while (1) {
            t1 = x0->field_8 != 0;
            x8 = (int32_t)(x0->field_0 + x8);
            x0 = x0->field_8;
            if (!t1) break;
        }
    }
    return x8;
}

Both products offer decompilation, graph navigation and MCP integration. rdis emphasizes a browser-first, multi-session workspace and one bounded caller/callee graph exposed consistently in the GUI, CLI, console and MCP. Hopper emphasizes a native analyst workflow with editable graph nodes and PDF export. This is a feature-scope comparison, not an accuracy ranking. Graph rendering and navigation are regression-tested in Chromium and Firefox (CI).

Decompiled output types its API calls from a library of 206 system prototypes (libc, POSIX, CoreFoundation and the Objective-C runtime), and Objective-C methods come out as valid Objective-C.

Install from GitHub.

rdis needs Python 3.9 or newer and git. Everything installs into its own virtual environment, nothing system-wide.

Paste this once. It makes the environment, installs rdis from GitHub and starts it.

        Step 3
        
Start rdis.
